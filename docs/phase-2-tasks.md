# Phase 2 — Schema, triggers, sealed link, proofs

Drafted at the Phase 1 gate; built by the unattended Phase 2 session on 2026-10-26 (D-31..D-36, O-11). Where the build departed from the draft text the item says so. Phase 1's engine (`src/tally/`) is the only tally code; Phase 2 gives it tables to run against and proves the database cannot undo what it says. Shape fixed by D-19, D-20; PRD P0-6; brief §8 "Sealed link". Decide O-10 and the E-9 question (item 2.0) first.

- [x] **2.0 Decide before the first migration.** *Done as D-31 (option i: `BallotStatusEvent`, and `Ballot` carries no status column at all), D-32 (O-10 kept: no `bps_as_of` published), D-33 (the `quorum_app` role assumed with `SET LOCAL ROLE`), D-34, D-35, D-36; O-11 opened.* (a) **E-9 at cast time vs D-19.** D-26 re-labels an *earlier* counted proxy ballot `PROXY_SUPERSEDED_BY_OWNER` when the owner casts directly. The engine does it in memory; on tables, "a ballot is never edited" (D-19) collides with changing that row's `status`/`code`. Options for Shane: (i) `Ballot.status`/`code` stay append-only and a `BallotStatusEvent(ballot_id, status, code, at, cause_ballot_id)` row carries the supersession, the current state being the latest event — the recount derives it in `(cast_at, ballot_id)` order anyway; (ii) the trigger permits exactly one transition (`COUNTED` → `REJECTED:PROXY_SUPERSEDED_BY_OWNER`, caused by a later direct cast for the same unit) and refuses everything else. Default proposed: (i), because the recount from `Ballot` rows alone (D-20) must reproduce E-9 from the rows regardless, so a status column on `Ballot` is a display cache in either design. (b) **O-10**: whether `Ballot` and the published list carry `bps_as_of` (the engine needs the share at cast time either way; the question is only whether it is published). (c) Record both in `docs/decisions.md` and, if (b) changes C-6, regenerate the fixtures per the fixture rule before any test reads them.
- [x] **2.1 Clone schema file and first migration.** *Built with two departures: no `Contest`/`Candidate` tables — the meeting definition is one JSONB column validated by the engine's schema on every read (D-35 a); `LedgerKind` has the three kinds E-4 reads, `CREDIT` comes with Phase 3 (D-35 c). CI also runs `prisma migrate diff --from-migrations --to-schema --exit-code`.* `prisma/schema/quorum.prisma`: `Meeting` (org-scoped; `rulesJson`, `rulesHash` = sha256 of the canonical rules, `openedAt`, `closedAt`, `sealedAt`, `salt`, `status OPEN|CLOSED`), `Contest`, `Candidate`, `Unit`, `UnitShare(effectiveFrom CHAR(10))`, `Owner`, `Ownership(fromDate, toDate CHAR(10))`, `LedgerEntry` (Phase 3 writes; Phase 2 reads for E-4/E-5), `Proxy`, `Ballot`, `BallotSecret` (D-20). **No `@db.Date`, no `timestamptz` for the meeting axis**: `castAt`, `receivedAt`, `revokedAt`, `openAt`, `closeAt` are `CHAR(19)` strings with a `CHECK` on the D-8 regex; the audit columns the foundation owns stay as they are. Integer `Int` for bps and cents with `CHECK >= 0`. The migration's hand-written half also `DROP`s `BillingAccount` and `StripeEvent` (D-27 c). *Acceptance:* `prisma validate`, `migrate deploy` from scratch on a throwaway database in CI, a schema test asserting no `date`/`timestamp` column exists on the Quorum tables, `foundation:drift` clean.
- [x] **2.2 Append-only triggers.** `quorum_append_only()` raising on UPDATE/DELETE of `Ballot`, `Proxy`, `BallotSecret`, `LedgerEntry` (and `BallotStatusEvent` if 2.0(a)(i)). Raise with the default SQLSTATE and a message naming the table (Gavel D-36: Prisma drops custom SQLSTATEs' messages on some mappings; test the error shape you actually get, not the one you intend). *Acceptance:* a migration test applies the file from scratch and provokes each refusal; the error text reaches the application as a typed `AppendOnlyViolation`.
- [x] **2.3 Load the roster from fixtures (read-only fixtures, write-once tables).** `scripts/quorum-load.ts` loads `units`, `unit_shares`, `owners`, `ownerships`, `assessments`, `proxies` and `meeting.json` into one org. Idempotent: a second run writes nothing (compare every column, not counts — Bookable A-045). *Acceptance:* row counts 120/124/138/141/2627/49; the second run's diff is empty.
- [x] **2.4 Cast path.** *"Replayed in file order" was wrong — file order is id order, not an arrival order; the replay casts in `(cast_at, ballot_id)` order and the cast path refuses a cast from the past (D-36). The close `CHECK` is on the meeting being closed, not on `castAt >= closeAt` (D-34).* `castBallot({meetingId, unitId, castBy, viaProxyId, choices, castAt})` in one transaction: runs `ballotRejectCode` (Phase 1, unchanged) against the live roster as of the record date and the unit's current counted ballot; generates the 128-bit nonce (the ONLY randomness, outside `src/tally/`); writes `Ballot` (`unitHash = sha256(meetingId|unitId|salt)`, `bpsAsOf`, `castAt`, `choices`, `nonceHash`, `receipt`, `status`, `code`) and `BallotSecret(ballotId, unitId, castBy, viaProxyId)` through a `SECURITY DEFINER` function; returns the receipt and nonce once. E-9 per 2.0(a). *Acceptance:* the 113 fixture ballots replayed through `castBallot` in file order produce the same 113 statuses/codes as `expected_ballots.csv`; a cast at or after `closeAt` is refused by the engine AND by a `CHECK`/trigger on `Ballot` (`castAt < meeting.closeAt`).
- [x] **2.5 Close and seal.** `closeMeeting(meetingId)`: sets `closedAt`, computes the tally from `Ballot` rows alone (the Phase 1 engine over `(unitHash, bpsAsOf, castAt, viaProxy flag, choices, status, code, receipt)`), stores the per-contest totals and commitments and the meeting commitment once, sets `sealedAt`, and a trigger `REVOKE`s `SELECT` on `BallotSecret` from the application role. **Idempotent:** a second close writes nothing and returns the stored commitments. *Acceptance:* commitments equal `expected_results.csv` on the loaded fixture; closing twice leaves one row of each; `foundation:drift` clean.
- [x] **2.6 Recount from `Ballot` rows.** `recountMeeting(meetingId)` = Phase 1 engine over `Ballot` rows with no join to `BallotSecret` or the roster. The engine entry point for this is a thin adapter: `Ballot` rows → the `BallotResult[]` shape → `quorumStatus`, `tallyElection`, `tallyResolution`, `merkleRoot`, commitments. *Acceptance:* equals the Phase 1 commitments on the fixture loaded through 2.4; the published list exported from `Ballot` equals `published_ballots.csv` byte for byte (if O-10 leaves C-6 as is).
- [x] **2.7 Tamper tests.** *The third assertion reads "an `INSERT INTO "Ballot"` for a closed meeting fails" (D-34).* As the app role after close: `SELECT * FROM "BallotSecret"` fails with `42501`; `UPDATE "Ballot" SET choices = …` fails on the trigger; `INSERT INTO "Ballot"` with `castAt >= closeAt` fails; the recount still equals the stored commitments. As a superuser in the test: flip one `Ballot.choices` after disabling the trigger → the recount's commitment differs from the stored one (the proof that the commitment binds the rows). *Acceptance:* each failure asserted on its SQLSTATE or message, not on "it threw".

Phase 2 exposes it as a server action; the screen is Phase 3.
