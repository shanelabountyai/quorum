# Phase 3 — UI, dues ledger, violations (DRAFT, written at the Phase 2 gate; not started)

Draft by the unattended Phase 2 session at the gate, for Shane's review. Nothing here is built. Phase 2 left a write layer with no screens: `src/meetings/` (cast, close, recount, published export, eligibility snapshot), all running as `quorum_app`. Phase 3 puts pages and server actions in front of it, adds the dues ledger (D-21) and the violation workflow (D-22), and queues notices to the outbox (never sent). Decide O-11 and the Phase 3 questions in item 3.0 first.

- [ ] **3.0 Decide before the first page.** (a) **O-11**: keep the table-wide `REVOKE` (D-33) or move the seal to a row-level-security policy keyed on `Meeting.closedAt` (per-meeting; the 2.7 test then asserts an empty result, not `42501`). (b) **Who casts in the UI.** A foundation `User` is not an `Owner`; an `Owner` is a roster row with a synthetic email. Options: an `OwnerLink(ownerId, userId)` table written by invite acceptance (the invite's email matches `Owner.email`), or a desk-only Phase 3 where board/manager users cast on an owner's behalf and record `castBy` from a dropdown. Default proposed: the link table, with a desk path too. (c) **Ballot id minting** stays `B-NNN` (D-35 f) or becomes a random public id (the sequential id reveals arrival order on the published list; the list is sorted by receipt, so order is only visible to someone who sorts by id). (d) **`CREDIT` in the ledger** (D-21): add it to `LedgerKind` AND to the engine's E-4 (a CREDIT reduces the balance like a PAYMENT), with a decisions entry, a golden case (GQ-12) and a fixture regeneration if the fixture ledger gains one. (e) **Deployment role** (D-33): the runtime `DATABASE_URL` should log in as a member of `quorum_app` only; record how the dev laptop and any future Neon database get that role.
- [ ] **3.1 Meeting pages (board/manager).** `/o/[org]/meetings` (list; status OPEN/CLOSED, record date, window), `/o/[org]/meetings/[id]` (definition read-only from `Meeting.definition`; contests; the eligibility snapshot from 2.8 behind `eligibilityScope`; the close button). Server actions `createMeeting` (from a pasted or uploaded `meeting.json`, validated by `parseMeeting`), `closeMeeting` (owner/admin, MFA-gated like the foundation's destructive actions; idempotent). Every action is an `orgAction` with a zod schema so the INV-01..04 harness attacks it; `tests/fixtures/app.ts` seeds `ref('meeting')`, `ref('unit')`, `ref('owner')`. *Acceptance:* harness green; a member cannot close; closing twice is one row.
- [ ] **3.2 Cast page.** `/o/[org]/meetings/[id]/vote`: the ballot form built from the contests (an election is up to `seats` checkboxes, a resolution is YES/NO/ABSTAIN), direct or via a proxy the caster holds, `castAt` from the server clock on the meeting axis (one module converts the instant to the meeting's wall clock under `rules.timezone_label`; the engine never does). The receipt and the nonce are shown ONCE with the D-2 wording ("proves inclusion; does not hide how you voted from anyone you show it to"). A rejected ballot shows its code and the receipt. *Acceptance:* an e2e casts, sees the receipt, and `tally:verify` accepts it after close; a second cast for the unit shows `DUPLICATE_UNIT`; the sealed link is not readable on any page.
- [ ] **3.3 Results and the published list.** `/o/[org]/meetings/[id]/results` after close: the §11 table from `ContestResult` + `Meeting`, every contest with its commitment, quorum with direct/proxy/total, the by-basis table, the informational other mode, `TIE_UNRESOLVED` with the tied ids and "the board runs a runoff (O-5)". `/o/[org]/meetings/[id]/published.csv` — the C-6 export (`publishedCsv`), and a receipt lookup box (`tally:verify` in the page). The D-2 limits sentence on every screen that shows a receipt or a commitment. *Acceptance:* the page's numbers equal `docs/EVAL.md`; the CSV download equals `published_ballots.csv` on the fixture.
- [ ] **3.4 Roster pages.** Units (share history as of a date), owners, ownerships, proxies for a meeting (received, revoked — a revocation is a new `ProxyRevocation` row, D-35 i, read by the engine as `revoked_at`). Import from CSV through `loadRoster` (write-once; a differing re-import shows `RosterDiffers`). *Acceptance:* the fixture imports from the page; a second import shows "0 inserted, every column matches".
- [ ] **3.5 Dues ledger (D-21).** `LedgerEntry` gains `CREDIT` and `reversesEntryId` + `reason` (append-only stays). A monthly dues run posts `monthly_budget_cents × share_bps / 10000` per unit with the integer remainder on the association's `ROUNDING` memo line so the month sums to the budget exactly — port Gavel's `money.ts` (LoanBook lineage) for the integer division, record the lineage. A passed special assessment posts one CHARGE per unit tagged with the resolution id. Unit statement page with the balance as of a date (E-4). *Acceptance:* the fixture's $35,000 month posts 120 charges summing to 3,500,000 cents with a 0 remainder; a $35,001 month posts a 1-cent ROUNDING line; `balanceCents` on the page equals the engine's.
- [ ] **3.6 Violations (D-22).** `Violation` + `ViolationEvent` (append-only), the state machine as data (`violations/transitions.json`), `TRANSITION_INVALID` on anything else, `FINE_ASSESSED` posting the `FINE` ledger row in the same transaction, notice and hearing dates on the calendar axis. Pages: list, detail with the event trail, the transition form. *Acceptance:* every legal transition has a test, every illegal one is refused with the code, the fine appears on the unit's statement.
- [ ] **3.7 Outbox notices.** Meeting notice (window, record date, agenda) and violation notices are queued to the foundation's outbox as `QUEUED` and never sent (`EMAIL_ENABLED` stays off; `required-modules.ts` gains `notifications`). *Acceptance:* a queued row per recipient; nothing leaves (the capture transport shows them).
- [ ] **3.8 Accessibility and e2e.** axe on every new page in both colour schemes (Bookable A-096's lesson: measure dark too); Playwright flows: create meeting → import roster → cast → close → results → verify a receipt. *Acceptance:* 0 axe violations; the e2e runs against the production build in CI.
- [ ] **3.9 Phase 3 gate.** `docs/EVAL.md` gains the ledger and violation numbers; README's "What is here" lists the screens; `NEXT.md`; PR against `main`, not merged.

**Exit criteria:** a board member can create a meeting, import the roster, watch owners cast, close, publish the list and the commitments, and recount — all from pages; a member can cast and verify a receipt and cannot see the sealed link or another unit's dues; the dues run and the violation workflow post to an append-only ledger; nothing is sent; CI green including e2e and axe.
